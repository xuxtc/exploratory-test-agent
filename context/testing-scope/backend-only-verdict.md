# Backend-Only Ticket Verdict Rule

## When this rule applies

A ticket's PR diff contains **only backend code** (services, routes, types, config — no `.tsx`/frontend component files), AND the ticket has **no associated frontend sub-tickets or related tickets** (no children, no `relatedTo` links pointing to a frontend card).

Check both conditions before applying:
1. Read `01-pr-diffs.json` — confirm every changed file is backend-only (`.ts` service/route/type files, `.json` config, test files). If any `.tsx` or frontend component appears, this rule does not apply.
2. Read `01-fetch.json` — confirm the ticket has no `parent`, no children, and no attachments referencing a frontend ticket. If there is a linked frontend ticket, do not apply this rule — the E2E test scope belongs to that ticket.

## What it controls

**Do not judge the ticket as FAIL solely because no frontend UI exists.** The acceptance criteria for a backend-only ticket are the API endpoints responding correctly — not a visible UI card.

## Verdict and comment rules

- **Verdict:** PASS if all verifiable backend API endpoints respond as expected. FAIL only if an API returns an unexpected status or wrong response body.
- **Scenarios:** Replace UI-driven scenarios with direct API calls (via `evaluate_script` → `fetch`). Verify each route the PR adds or modifies:
  - Status endpoints: call and assert response shape.
  - Mutation endpoints: call and assert idempotent success (or correct error on missing state).
- **Notable findings:** Always include an `[Info]` bullet stating that no frontend code was included in this PR and that E2E UI flows (connect/status display/disconnect UI) are deferred until a frontend card is delivered.
- **Do NOT mark scenarios as FAIL with `screenshot_omit_reason: "no UI surface"` for every scenario** — that produces a misleading all-FAIL result for a ticket whose backend work is complete.

## Example — scenario verification

PR adds `GET /v3/connector/gmail/status` and `POST /v3/connector/gmail/disconnect`. No frontend code. No frontend related ticket.

✅ Test: `GET /api/v3/connector/gmail/status` → `200 {"authenticated":false}` for unauthenticated user.  
✅ Test: `POST /api/v3/connector/gmail/disconnect` → `200 {}` (idempotent, no token).  
**Verdict: PASS**

Notable findings: `[Info]` No frontend card — Gmail connector card UI not yet shipped. E2E OAuth connect/disconnect flows deferred.

## Linear comment template

Use this exact structure for backend-only tickets. Copy and fill in the blanks.

```
**Result:** PASS  ·  **Env:** <prod|stg>

### Summary
Backend <phase/feature name> APIs are deployed and responding correctly. No frontend UI code was included in this PR — E2E UI validation is pending a frontend card.

### Scenarios

| **Test Point** | **Test Steps** | **Expected Result** | **Test Result** |
| -- | -- | -- | -- |
| <Feature name> API — <state description> | 1. Call `<METHOD> <path>` as logged-in <role> user <with/without> <precondition>. | Returns `<status> <response shape>`. | ✅ Pass |
| <Feature name> API — <state description> | 1. Call `<METHOD> <path>` as logged-in <role> user <with/without> <precondition>. | Returns `<status> <response shape>`. | ✅ Pass |

**Test Point naming rule:** Use a human-readable feature/function name, not the raw HTTP method + path. Format: `<Feature name> API — <state description>`. Example: `Gmail status API — unauthenticated user`, NOT `GET /gmail/status — unauthenticated`. The HTTP method and path belong in the Test Steps column, not the Test Point column.

### Notable findings
- **[Info]** No frontend code in this PR — <describe what UI is missing, e.g. "the Gmail connector card UI"> is not yet shipped. E2E <describe the flows, e.g. "connect/disconnect/status UI flows"> cannot be tested until a frontend card is delivered. <Those scenarios> are deferred to that follow-up.

### Evidence
```
